# IronLog Audit Remediation Design

**Status:** Compatibility implementation, deterministic gates, and UI cleanup completed and integrated locally on `main` on 2026-08-12. Production rollout and strict revision enforcement remain open.

## Purpose

Resolve the verified lifecycle-integrity, quality-gate, accessibility, and UI-polish findings from the 2026-08-12 `agent-sanity-review` and `ui-quality-gate` scans. The work is split into three independently reviewable streams so lifecycle safety can ship first without coupling it to cosmetic cleanup.

## Global Constraints

- `activeSessions/{uid}` is the canonical source for workout finalization.
- The browser never creates or updates `workouts`, `closedSessions`, `exerciseSessions`, or `records` directly.
- `exerciseSource: 'global' | 'user'` remains mandatory throughout the lifecycle.
- Firestore weights remain kilograms; UI-only unit conversion stays unchanged.
- Vercel functions remain Node.js functions because Firebase Admin SDK is required.
- No new dependency is needed. Use `crypto.randomUUID()`, existing validation helpers, existing sync UI, and existing emulator harnesses.
- The rollout must tolerate old browser tabs during a short compatibility window without accepting client-supplied workout contents.

## Stream A: Canonical Workout Closure

### Chosen contract

Every active-session write gets a fresh opaque `sessionRevision` generated by the browser with `crypto.randomUUID()`. Before finishing, the client freezes its current session snapshot, writes that exact snapshot to `activeSessions/{uid}`, and receives the revision it wrote. It then calls `/api/finalize-workout` with only:

```ts
interface FinalizeWorkoutRequest {
  sessionId: string
  sessionRevision?: string
}
```

During the compatibility phase, `sessionRevision` is optional. Legacy finalize fields may be accepted by the request parser so old tabs do not break, but the server ignores their values. The server always derives the workout from the active-session document.

### Server transaction

The server obtains one `closedAt` timestamp before starting the transaction. Inside the transaction it:

1. Reads the deterministic workout, tombstone, and `activeSessions/{uid}` documents.
2. Preserves current idempotency: an already finished matching closure returns its existing result before requiring a live active session.
3. Verifies ownership and `sessionId`.
4. When the request contains `sessionRevision`, compares it with the stored revision. A mismatch raises HTTP `409` with code `active_session_changed` and performs no writes.
5. Converts the active draft into the finished workout:
   - identity, `startedAt`, `templateId`, label, exercise IDs, sources, and names come from `activeSessions`;
   - only sets with `done === true` are included;
   - weight and repetitions are parsed and validated with the existing server limits;
   - exercises without completed sets are removed;
   - at least one completed set is required;
   - `finishedAt` is the server timestamp capped by `MAX_ACTIVE_SESSION_AGE_MS`.
6. Creates the workout and tombstone from that canonical normalized value, derives projection keys from the same exercises, and deletes the active session atomically.
7. Runs the existing idempotent materialization step after the transaction.

Malformed active-session contents fail before any write. A stale or modified request body can no longer change workout history.

### Client closure flow

`beginClosure('finish')` continues to freeze the local snapshot and stop debounced persistence. A new preparation operation explicitly writes that frozen snapshot and returns its `sessionRevision`.

- If preparation succeeds, the closure request uses `{ sessionId, sessionRevision }`.
- If preparation fails, no closure request is sent. The unsent closure intent is cleared, editing is unlocked, `activeSessionSyncStatus` becomes `failed`, and the existing retry-sync banner is shown.
- If the server returns `active_session_changed`, the request is definitive, not ambiguous. The client clears the stale intent, reloads the authoritative active session, and shows precise copy explaining that the session changed on another client and must be reviewed before finishing again.
- If the response is lost after a successful server commit, the existing closure intent and deterministic ID still drive the current idempotent retry path.

### Empty and stale sessions

The product contract requires at least one completed set for a saved workout. Confirming an empty finish therefore calls `/api/discard-session`, with copy that says the session will be closed without saving a workout. It never calls `/api/finalize-workout`.

When continuing a stale session, the refreshed local session remains available if its write fails. The hook sets sync status to `failed` and returns an explicit sync-failure outcome instead of claiming that restoration itself failed. The page shows a local-recovery message and the existing retry-sync action.

### Compatibility rollout

The rollout has two deployments:

1. **Compatibility deployment:** API accepts the new request and legacy request fields, ignores all client workout contents, and treats `sessionRevision` as optional. Firestore rules allow either legacy active documents or active documents with a valid revision. The new SPA always writes a revision and always sends the fenced request.
2. **Enforcement deployment:** after the compatibility deployment and SPA are live, the API requires `sessionRevision`, Firestore rules require it on active sessions, and legacy finalize fields are rejected. Deterministic emulator tests must pass against the strict contract before rollout.

There is no dual-write path and no migration of completed workouts.

### Alternatives rejected

- **Continue treating the finalize body as canonical:** preserves the verified integrity bug and is rejected.
- **Use only `updatedAt` as the fence:** couples correctness to client clocks and timestamp collisions; rejected in favor of an opaque revision.
- **Require the revision immediately:** breaks already-open tabs unnecessarily; rejected in favor of the two-stage rollout.
- **Merge client and server session contents:** creates conflict-resolution behavior the product does not need; rejected.

## Stream B: Deterministic Quality Gates and Accessibility

- Playwright uses zero retries whenever `E2E_BACKEND=emulator`; one retry remains available only for live runs.
- The readiness panel entrance animation uses opacity and translation, not scale, so its 44-pixel controls never shrink below their hit-area contract.
- The existing accessibility/contrast command must pass on the first attempt with no flaky result.
- The dashboard Enter-key deletion test seeds and cleans up its own workout through the emulator helper. It no longer skips because a shared account is empty.
- `tests/e2e/dashboard.spec.ts` joins the deterministic isolated emulator command.

No new visual-regression framework or CI system is introduced.

## Stream C: UI Polish and Cleanup

- Dashboard peak-day copy uses the existing `polishPlural` helper so one set renders as `1 seria`.
- The progress heatmap formats its visible peak date with the existing Polish date style. Its accessible summary uses the same localized date rather than ISO text.
- `src/App.tsx` is deleted because `src/main.tsx` mounts `AppRouter` directly and no caller imports `App`.

## Testing Strategy

### Lifecycle

- Parser unit tests prove that compatibility requests accept legacy fields but return only `sessionId` and optional `sessionRevision`.
- Validation unit tests cover active drafts with unfinished sets, malformed completed sets, empty completed output, and server-derived timestamps.
- Integration tests prove that divergent client fields are ignored, revision mismatches perform zero writes, concurrent finish remains idempotent, legacy unfenced requests remain canonical during compatibility, and strict enforcement rejects missing revisions.
- Hook/page tests cover preparation-write failure, `active_session_changed`, stale-session sync failure, and empty-session discard.
- Workout E2E proves the final saved workout matches the frozen active snapshot and retains acknowledgement-loss recovery.

### Gates and UI

- Accessibility E2E measures at least 44 by 44 pixels with emulator retries disabled.
- Dashboard E2E proves Enter opens the delete confirmation against a deterministic fixture.
- Dashboard unit coverage asserts singular set copy.
- Progress page coverage asserts the localized visible and accessible peak date.
- Every stream finishes with lint, relevant focused tests, all unit tests, production build, and its relevant emulator suite.

## Delivery Order

1. Stream A compatibility deployment: server canonicalization and optional fence, then SPA fenced closure.
2. Stream B deterministic gates and accessibility.
3. Stream C polish and dead-file cleanup.
4. Stream A enforcement deployment after the compatibility release is confirmed live.

Stream B may be merged before Stream A if desired, but Stream A remains the release priority because it protects permanent workout history.
